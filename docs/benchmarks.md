# Benchmarks

Generated by `scripts/bench-strategies.sh` on 2026-11-28.
Raw Gatling reports: `proof/phase1-local/tests/gatling-*`.

**Stack:** nginx round-robin to 2 auth-service instances, Postgres 17, Redis 7, Kafka (KRaft), DynamoDB Local, all in Docker Desktop (WSL2) on a Windows laptop, with the Gatling JVM on the same machine.
Absolute numbers are therefore bounded by that environment (about 300 req/s through the Docker network even for `/actuator/health`); the *differences between strategies* are what matter.
Latencies are client-side (Gatling), in milliseconds.

## Burst: 1000 concurrent authorisations of ¥1000 on one ¥100000 card

Exactly 100 may be approved. `overspend` = approved × amount − limit. Users are injected over 3 s (Docker Desktop refuses part of a 1,000-connection SYN burst), so ~all 1000 requests are in flight together.

| strategy | approved | declined | overspend ¥ | p50 ms | p95 ms | p99 ms | req/s | failed |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| naive | 1000 | 0 | 900000 | 7368 | 9458 | 10401 | 91.7 | 0 |
| db-pessimistic | 100 | 900 | 0 | 9824 | 12046 | 12322 | 67.5 | 0 |
| db-optimistic | 100 | 900 | 0 | 9020 | 11116 | 11832 | 83.2 | 0 |
| redis-lock | 100 | 900 | 0 | 9400 | 14019 | 14844 | 63.8 | 0 |
| redis-lua | 100 | 900 | 0 | 3225 | 4648 | 5216 | 155.4 | 0 |
| db-pessimistic (platform threads) | 100 | 900 | 0 | 11061 | 13742 | 14070 | 60.3 | 0 |

- `naive` (read-then-write, no lock) approves far more than the limit allows. See [INC-001](incidents/INC-001-overspend-naive.md).
- `db-pessimistic`, `db-optimistic`, `redis-lock` and `redis-lua` approve exactly 100 and overspend ¥0.
- `redis-lua` does check-and-hold in one atomic script, so it never queues on a row lock, a distributed lock or version-conflict retries, and it has the lowest latency of the safe strategies.

## Virtual threads (db-pessimistic, burst)

| threads | p50 ms | p95 ms | p99 ms | req/s |
|---|---:|---:|---:|---:|
| virtual (`spring.threads.virtual.enabled=true`) | 9824 | 12046 | 12322 | 67.5 |
| platform (Tomcat 200 worker threads) | 11061 | 13742 | 14070 | 60.3 |

With platform threads, at most 200 requests are in flight inside Tomcat; each blocks on the Hikari pool or the row lock, so the rest queue at the connector. Virtual threads park cheaply while waiting, so all 1000 requests can be in flight. Here the DB row lock and a 20-connection pool are the real limit, so the gain is modest; the benefit shows on strategies that wait on I/O instead of a lock.
